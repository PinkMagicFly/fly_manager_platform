## 一、项目概述与开发目标

### 1.1 业务背景与系统定位
低空经济已成为国家战略性新兴产业，随着无人机物流配送、低空巡检、医疗紧急转运等业务的爆发式增长，低空飞行活动频次指数级攀升。然而，传统低空运营普遍存在**空域供需矛盾突出、飞行计划审批周期长、在途监管手段匮乏、多主体信息割裂、安全责任难以穿透界定**等痛点。

本项目建设“**翔云·低空智慧物流运营平台**”，旨在构建城市级/区域级低空物流运营的一体化数字底座。平台基于B/S与移动端混合架构，建立“规范申报、智能调度、实时在途监控、数字结算对账、合规安全闭环”的数字化业务运营体系。

### 1.2 核心业务闭环
平台贯通核心端到端主链路，形成不可逆与严密审计的闭环：
$$\text{客户下单} \longrightarrow \text{合规校验与费用试算} \longrightarrow \text{商户接单} \longrightarrow \text{智能资源调度} \longrightarrow \text{飞行计划在线申报与审批} \longrightarrow \text{在途多维监控与告警} \longrightarrow \text{送达签收} \longrightarrow \text{自动出账与对账开票}$$

### 1.3 服务角色与功能中心划分
平台覆盖六类核心业务角色及一类外部公众：
1. **商户（低空物流企业）**：入驻资质备案、子账号授权、订单承接调度、飞行计划申报、机队与排班管理、对账发票申请、企业驾驶舱查看。
2. **客户（下单个人/企业）**：地址簿管理、快速/批量/预约下单、费用预估与支付、在途轨迹实时查看、签收确认、服务评价与投诉。
3. **平台管理员**：商户资质审核、实名认证审核、飞行申报审批、全局订单与异常接管、定价规则与参数配置、审计日志监控、运营总驾驶舱。
4. **空管监察员**：空域网格与管制动态监管、飞行计划合规复审、临时管制指令下发、违规轨迹侦测与执法留痕。
5. **机长（飞手）**：移动端作业工作台、调度任务确认、航线与气象确认、执行起飞/在途上报/降落确认、设备故障紧急上报。
6. **运维专员**：无人机健康度监测、场站设施巡检、维保工单执行、场站预约审批。
7. **第三方与公众**：周边空域活动告示查看、公众建议与投诉反馈。

平台横向划分为**七大功能中心**：
- **账户与权限中心**：多端统一认证、RBAC动态授权、商户企业资质审核、操作审计。
- **订单运营中心**：订单全生命周期状态流转、服务空域校验、智能阶梯计费、调度工作台、结算账单管理。
- **机队资产中心**：“人-机-场”台账、无人机五态模型、场站一张图与预约防重、机组资质与周排班矩阵。
- **空域合规中心**：禁飞/限飞/管制三区空间可视化、航线合规毫秒级校验、飞行计划在线申报与审批流、违规案件处置闭环。
- **数据洞察中心**：按角色差异化呈现的运营驾驶舱、时效与利用率分析、自助式多维报表生成。
- **应急与服务中心**：三级告警引擎（一般/严重/紧急）、应急处置时间线留痕、多方协同处置、客服工单台与多渠道消息触达。
- **平台治理中心**：系统运行参数配置、外部三方接口网关监控、数据备份策略与审计日志检索。

### 2.2 后端分层架构与领域规则
后端工程采用“**严格单向调用分层体系**”与“**状态机驱动领域设计**”，划分为以下四个层次：
```
┌────────────────────────────────────────────────────────┐
│   接入层 (API Layer): Controller / Interceptor / DTO    │
│   - 协议转换、参数JSR-303强校验、Client-Kind双端裁剪器    │
└───────────────────────────┬────────────────────────────┘
                            │ (调用)
┌───────────────────────────▼────────────────────────────┐
│   应用层 (Application Layer): Service / Command / Event │
│   - 业务用例编排、跨领域事务控制(@Transactional)、事件发布│
└───────────────────────────┬────────────────────────────┘
                            │ (调用)
┌───────────────────────────▼────────────────────────────┐
│   领域层 (Domain Layer): Entity / StateMachine / Rules  │
│   - 核心业务实体、状态机流转守卫、电子围栏空间算法校验   │
└───────────────────────────┬────────────────────────────┘
                            │ (调用)
┌───────────────────────────▼────────────────────────────┐
│   基础设施层 (Infrastructure Layer): Mapper / Gateway   │
│   - MyBatis持久化、Redis缓存客户端、空间类型TypeHandler │
└────────────────────────────────────────────────────────┘
```

**后端三大核心开发硬性守则**：
1. **状态变迁必须经状态机统一守护**：
   - 订单九态（`10待支付` $\rightarrow$ `20待接单` $\rightarrow$ `30待调度` $\rightarrow$ `40待起飞` $\rightarrow$ `50飞行中` $\rightarrow$ `60已送达`；异常支线：`70已取消`、`80异常中断`）。
   - 申报四态（`0待审批` $\rightarrow$ `1已通过` / `2已驳回` / `3已撤销`）。
   - 设备五态（`0闲置` $\rightarrow$ `1任务中` $\rightarrow$ `2维保中` $\rightarrow$ `3故障` $\rightarrow$ `4离线`）。
   *严禁直接通过 SQL 或 Mapper 更新 `state` 字段，所有更新必须携带流水记录（如 `order_state_flow`）并经校验！*
2. **双端数据自适应裁剪（Client-Kind Adapter）**：
   - 前端请求头统一携带 `Client-Kind: pc` 或 `Client-Kind: app`。
   - 接入层通过 ResponseBodyAdvice 拦截器结合 Jackson 动态过滤白名单，PC 端下发全量视图，移动端下发精简报文（省流量、响应 < 1.5s），业务层代码 100% 复用。
3. **全局异常与审计规范**：
   - 统一接口出参格式：`Result<T> { code: 200, message: "操作成功", data: T, timestamp: 1718000000000 }`。
   - 所有单据表强制包含审计三件套：`created_at (DATETIME)`, `updated_at (DATETIME)`, `is_deleted (TINYINT)`。


### 2.3 数据库物理设计规范与27张表全景
采用数据库 `soarcloud_lae`，字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci`。全库按7大数据域共规划27张核心数据表：

| **账户域** | `uam_account` | 统一账户主表（多角色合一） | 登录名/手机号唯一，密码Argon2id哈希，存储账户类别与状态 |
| | `uam_role` | RBAC角色定义表 | 预置平台管理员、商户、空管监察员、机长、运维等角色 |

| | `uam_role_grant` | 角色-权限(菜单/按钮)授权表 | 支撑菜单路由与按钮级颗粒度权限控制 |

## 五、核心技术难点专项攻坚方案

### 5.1 空间几何与空域冲突毫秒级校验
- **难点**：飞行申报与实时在途监管需在毫秒级判断航线（折线）是否穿越复杂多边形禁飞区，在高并发下全表几何运算会导致数据库 CPU 飙升。
- **攻坚策略**：
  1. **空间两级过滤机制**：
     - **粗筛（Bounding Box）**：利用 MySQL 8 空间索引对空域多边形与航线外接矩形（MBR）做 `MBRIntersects` 快速碰撞筛查，过滤 95% 无关空域。
     - **精判（Geometry Calculation）**：对候选区块调用 `ST_Intersects` 确认真交，并在领域层提取高度区间与时段区间做重叠精判。
  2. **内存预热与空间缓存**：将全市常态化禁飞区、限飞区多边形在系统启动时载入 Redis / 本地内存，利用 JTS（Java Topology Suite）在应用内存中执行初次拓扑过滤，将数据库压力降至最低。

### 5.2 接入层 Client-Kind 双端自适应报文裁剪
- **难点**：PC 端业务操作复杂，需要返回深度关联对象（如商户资质明细、多边形完整顶点、费用公式）；而移动作业端受限于移动网络与设备性能，若返回全量报文会导致流量浪费与渲染卡顿。
- **攻坚策略**：
  1. 统一在全局 `ResponseBodyAdvice` 实现中，依据请求头 `Client-Kind`（`pc` 或 `app`）动态切换 Jackson 过滤器。
  2. 当 `Client-Kind == app` 时，自动剥离审计三件套字段、空域复杂坐标数组、历史备注明细等，仅保留移动作业核心字段，移动端报本体积缩减 40%~60%，响应时间压缩至 1 秒以内，后端领域层与业务逻辑层完全复用。

### 5.3 飞行轨迹高频写入批聚合与按需抽稀回放
- **难点**：低空平台同时监控数百架无人机，每 1~2 秒回传一次坐标，峰值写入 QPS 极高；前端轨迹回放若渲染海量原始坐标点，会导致浏览器卡死。
- **攻坚策略**：
  1. **异步批聚合落库**：在 `monitor-alert` 接入层引入内存 RingBuffer / Redis List 作为缓冲队列，定时器每 200ms 或聚合满 100 条批量执行 MyBatis `insertBatch` 写入分区表 `fly_trace`，平滑数据库 IO 峰值。
  2. **道格拉斯-普克（Douglas-Peucker）算法抽稀**：移动端拉取历史回放轨迹时，服务端在查询后执行抽稀算法，在保证航线形态精度的前提下，抽离直线段上的冗余坐标点，返回数据量减少 80%。

### 5.4 跨服务多状态机协同与事务一致性
- **难点**：订单（九态）、飞行申报（四态）、无人机与机组（五态）三者高度联动（例如：调度确认需同时变更订单为待起飞、无人机为任务中、申报单为待审批；发生异常时需联动回滚），容易出现状态孤岛。
- **攻坚策略**：
  1. **统一领域状态机设计**：在各模块 `domain` 层内严格封装修订方法，禁止对外暴露实体 setter。
  2. **应用层编排与事务控制**：在应用层用例方法声明 `@Transactional(rollbackFor = Exception.class)`，跨实体状态变更统一在该事务中顺序提交，任一步骤失败（如机位预约冲突）立即整体回滚，并向 `order_state_flow` 准确记录流转失败日志。

### 5.5 移动端弱网离线暂存与静默同步机制
- **难点**：外场作业（起降场、偏远配送点）移动信号易受干扰，断网时机长无法报修或提交巡检，造成作业中断。
- **攻坚策略**：
  1. UniApp 端封装本地 SQLite / `uni.setStorage` 离线存储适配器。
  2. 当网络探测为离线或超时时，机长填报的故障工单、设备签到数据自动持久化在本地“待同步队列”中，并生成本地临时凭据。
  3. 监听网络状态变更事件，一旦网络恢复正常，后台工作线程自动按时间戳顺序静默重发队列中的离线请求，服务端根据单据防重令牌幂等处理，确保数据零丢失。

     - 测试所有合法状态的正向流转（如订单九态从待支付到已送达，申报四态从待审到通过）；
     - 严格测试非法流转与逆向跃迁（例如：未支付直接跳到待起飞、已送达订单重复调度），必须断言抛出预期的业务异常并回滚。
   - **核心业务算法与计算测试（Algorithm & Rules Testing）**：
     - 空间电子围栏校验：测试 MBR 粗筛算法、折线与复杂多边形相交算法，必须覆盖“包含、相交、相离、顶点相切、限高穿越”全部空间拓扑场景；
     - 阶梯多维运费试算：覆盖超里程、空域加权费、加急系数、满减优惠等组合，断言精度（精确至小数点后2位）；
     - 调度匹配打分：多约束条件（载重上限、续航电量、机长资质、场站容积）下的排他性最优推荐匹配。
   - **跨领域事务一致性与越权测试（Transaction & Security Testing）**：
     - 模拟调度确认过程中，生成申报单成功但场站锁定失败，断言 `@Transactional` 回滚机制生效，不残留脏数据；
     - 模拟伪造请求头或跨租户 Token 访问他人数据，断言系统精准拦截并返回 403 越权错误。
3. **质量门禁（Quality Gate）执行红线**：
   - **覆盖率指标**：`domain` 领域模型、状态机与核心算法代码的分支覆盖率 $\ge 85\%$；
   - **门禁校验指令**：每次模块交付或提交代码前，在后端根目录执行 `mvn clean test`，**必须 100% 绿灯通过，严禁存在被跳过（@Disabled）、失败（Failures）或报错（Errors）的测试用例**！

### 7.4 风险识别与降级应对预案

| 潜在风险点 | 风险等级 | 诱发原因 | 预防与应急降级预案 |
| :--- | :---: | :--- | :--- |
| **空间拓扑运算性能瓶颈** | **高** | 复杂多边形禁飞区碰撞计算在海量航迹下消耗大量 CPU | **预案**：建立双层过滤机制，先依靠 MySQL 空间索引 MBRIntersects 外接矩形做快速粗筛；若复杂多边形计算压力大，降级为服务端内存预载 JTS 几何缓存处理。 |
| **双端联调周期延误** | **中** | 前后端字段定义不一致或接口变动频繁 | **预案**：阶段0即行冻结 Swagger / Knife4j 接口契约，前后端定义标准 Mock 数据先行动工，联调阶段依据规范严格核验。 |
| **移动端跨端打包与环境异常** | **中** | UniApp 各端语法差异或平台 SDK 兼容问题 | **预案**：以移动端 H5 模式（标准响应式）与微信小程序作为基准开发验证环境，规避原生 App 签名及复杂环境配置风险，确保演示可用性 100%。 |
| **时间紧迫下的业务裁剪边界** | **低** | 开发进度落后导致无法全量覆盖 26 个页面 | **预案**：坚决贯彻“**主干优先、做深做透**”原则，死守“客户下单—商户接单—智能调度—合规审批—起飞在途—送达结算”核心主干链路，对报表设计器等辅助治理页面适度精简。 |
